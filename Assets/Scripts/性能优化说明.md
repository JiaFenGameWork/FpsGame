# 性能优化说明 - 解决卡顿问题

## 🐛 问题描述

场景每隔几秒会出现明显卡顿现象。

## 🔍 问题分析

通过代码审查，发现了以下性能问题：

### 1. **主要原因：寻路协程未分帧执行** ⚠️

**位置**：`Assets/Scripts/Physics/NePathFinder.cs` 的 `FindPathAsy` 方法

**问题**：
- 虽然使用了协程，但整个 A* 寻路算法在一帧内完成
- 代码中定义了 `slice` 变量但没有正确使用
- 原本的分帧逻辑 `if (slice >= 10f)` 频率太低，且位置不对

**影响**：
- 每次敌人请求新路径时，会在单帧内计算数千次节点
- 导致明显的帧率下降（卡顿）

### 2. **次要问题：重复的 GetComponent 调用**

**位置**：`Assets/Scripts/Enemy/AttackStyle/BallAttackLogic.cs` 的 `CheckHit` 方法

**问题**：
- 每帧对每个碰撞体调用 `GetComponentInParent<IDamageable>()`
- 同一个对象可能被重复检测和伤害
- `GetComponentInParent` 是昂贵的操作

## ✅ 解决方案

### 1. 优化寻路分帧逻辑

**修改前**：
```csharp
int slice = 0;
while (openSet.Count > 0)
{
    // ... 处理节点 ...
    
    foreach (Vector3Int neighborGrid in GetNeighbors(current.GridIndex))
    {
        // ... 处理邻居 ...
        
        slice++;
        if (slice >= 10f)  // 问题：频率太低，位置不对
        {
            slice = 0;
            yield return null;
        }
    }
}
```

**修改后**：
```csharp
int nodesProcessedThisFrame = 0;
const int maxNodesPerFrame = 50; // 每帧最多处理50个节点

while (openSet.Count > 0)
{
    // ... 处理当前节点 ...
    
    foreach (Vector3Int neighborGrid in GetNeighbors(current.GridIndex))
    {
        // ... 处理邻居 ...
    }
    
    // 每处理完一个节点后检查是否需要分帧
    nodesProcessedThisFrame++;
    if (nodesProcessedThisFrame >= maxNodesPerFrame)
    {
        nodesProcessedThisFrame = 0;
        yield return null; // 下一帧继续
    }
}
```

**优点**：
- ✅ 将寻路计算分散到多帧
- ✅ 每帧只处理 50 个节点，保证流畅度
- ✅ 可调整 `maxNodesPerFrame` 来平衡性能和响应速度

### 2. 优化碰撞检测缓存

**修改前**：
```csharp
private bool CheckHit()
{
    Collider[] hitColliders = Physics.OverlapSphere(...);
    
    foreach (var hitCollider in hitColliders)
    {
        // 每次都调用 GetComponentInParent（性能开销大）
        IDamageable damageable = hitCollider.GetComponentInParent<IDamageable>();
        if (damageable != null)
        {
            // 可能重复命中同一个对象
            OnHit?.Invoke(damageable);
        }
    }
}
```

**修改后**：
```csharp
// 添加缓存
private HashSet<Collider> _hitThisAttack = new HashSet<Collider>();

private bool CheckHit()
{
    Collider[] hitColliders = Physics.OverlapSphere(...);
    
    foreach (var hitCollider in hitColliders)
    {
        // 跳过已处理的碰撞体
        if (_hitThisAttack.Contains(hitCollider))
            continue;
        
        // 检测到可伤害物体时缓存
        IDamageable damageable = hitCollider.GetComponentInParent<IDamageable>();
        if (damageable != null)
        {
            _hitThisAttack.Add(hitCollider); // 标记为已处理
            OnHit?.Invoke(damageable);
        }
    }
}

// 攻击开始/结束时清空缓存
public bool TryStartAttack(Transform target)
{
    if (!IsAttacking) {
        _hitThisAttack.Clear(); // 清空缓存
        // ...
    }
}
```

**优点**：
- ✅ 避免重复命中同一个对象
- ✅ 减少不必要的 `GetComponentInParent` 调用
- ✅ 更符合游戏逻辑（一次攻击只命中一次）

## 📊 性能改进预期

### 寻路优化
- **原来**：单次寻路可能处理 1000+ 节点在一帧内 → 可能造成 100+ ms 延迟
- **现在**：每帧最多 50 节点 → 每帧延迟控制在 5ms 以内
- **结果**：消除了主要的卡顿来源

### 碰撞检测优化
- **原来**：每帧对每个碰撞体都调用 `GetComponentInParent`
- **现在**：同一次攻击中每个碰撞体只调用一次
- **结果**：减少了不必要的组件查找开销

## 🎮 使用建议

### 调整分帧参数

如果需要调整性能平衡，可以修改 `maxNodesPerFrame`：

```csharp
const int maxNodesPerFrame = 50; // 默认值
```

- **增加值（如 100）**：寻路更快响应，但可能轻微影响帧率
- **减少值（如 25）**：更平滑，但寻路响应稍慢
- **推荐范围**：30-100

### 其他性能建议

1. **限制同时寻路的敌人数量**
   - 可以考虑添加寻路请求队列
   - 避免多个敌人同时开始寻路

2. **降低寻路频率**
   - 不需要每次到达巡逻点都重新寻路
   - 可以缓存常用路径

3. **使用对象池**
   - 敌人生成/销毁可以使用对象池
   - 避免频繁的 GC

4. **Physics.OverlapSphere 优化**
   - 使用 NonAlloc 版本：`Physics.OverlapSphereNonAlloc`
   - 减少每帧的内存分配

## 🔧 如果还有卡顿

如果修改后仍有卡顿，可以检查：

1. **Unity Profiler**
   - Window → Analysis → Profiler
   - 查看 CPU 使用情况，定位具体瓶颈

2. **其他可能原因**：
   - 地形渲染
   - 粒子特效过多
   - 光照计算
   - GC（垃圾回收）

3. **进一步优化方向**：
   - 使用 Job System 并行化寻路
   - 使用 Burst Compiler 加速计算
   - 降低地形分辨率

## 总结

**核心问题**：寻路协程未真正分帧 → 单帧计算量过大 → 卡顿

**解决方案**：
- ✅ 添加正确的分帧逻辑（每帧 50 节点）
- ✅ 优化碰撞检测缓存
- ✅ 减少重复的组件查找

这两个优化应该能显著改善游戏的流畅度！
